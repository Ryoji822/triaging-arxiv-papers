# arXiv 論文トリアージ

広告代理店の実務者向けに、arXiv の新着から**実務に効く論文だけ**を抽出して届ける。

このスキルの価値は「たくさん集めること」ではなく「読まなくていい論文を捨てること」にある。
候補を全部並べたレポートは失敗である。

## 役割分担

- **スクリプト（決定論的）**: 取得・重複排除・既出除外・キーワード予備スコア
- **Claude（判断）**: 差分性の判定、実務価値の採点、S/A/B/C の振り分け、翻訳

予備スコアは LLM に渡す件数を絞るためだけのもの。**採否の根拠に使ってはいけない。**

## ワークフロー

このチェックリストをコピーして進行状況を追跡する:

```
トリアージ進捗:
- [ ] ステップ0: 実行範囲とSlack送付先を確認する
- [ ] ステップ1: 設定と既知トピック台帳を読み込む
- [ ] ステップ2: 候補を取得する（スクリプト実行）
- [ ] ステップ3: 既知との差分を照合する
- [ ] ステップ4: S/A/B/C に採点する
- [ ] ステップ5: レポートを生成する
- [ ] ステップ6: 品質チェックを実施する
- [ ] ステップ7: Slackに送付し、状態ファイルを更新する
```

---

**ステップ0: 実行範囲とSlack送付先の確認**

1. 期間を確定する。指定がなければ日次として扱い、`--daily` に曜日から決めさせる。「今週」なら `--days 8`
2. バケツの指定があるか確認する（なければ全9バケツ）
3. Slack送付が要るか確認する。**送付する場合、チャンネル名が指定されていなければ必ず尋ね、回答を待つ**。チャット表示だけで良い場合は送付をスキップして構わない

**無人実行では尋ねない。** 呼び出し側が範囲と送付先を渡す。渡されていなければ
送付をスキップし、レポートをファイルに書いて終わる。無人実行で人間の回答を
待つと、ジョブがタイムアウトするまで止まったままになる。

---

**ステップ1: 設定と台帳の読み込み**

- [config/settings.md](config/settings.md) — フィード構成としきい値の考え方
- [state/known-topics.md](state/known-topics.md) — **必読**。既知トピック。ここを読まずに採点すると毎回同じ話が上がる
- [reference/evaluation-criteria.md](reference/evaluation-criteria.md) — 採点軸

---

**ステップ2: 候補取得**

```bash
python3 scripts/fetch_arxiv.py --daily                               # 無人日次実行（曜日で窓を決める）
python3 scripts/fetch_arxiv.py --days 2
python3 scripts/fetch_arxiv.py --days 8 --bucket psych creative      # 領域を絞る
python3 scripts/fetch_arxiv.py --days 2 --include-rss --new-only     # 取り逃しを減らす
```

`--daily` は取得窓を曜日から決め、土日と「配信済みの日」をスキップする（詳細は
[config/settings.md](config/settings.md) の「日次実行」）。日数を一律に固定しないのは、
月曜の告知が金〜日の投稿をまとめて含むためである。窓を1日に固定すると月曜に金曜分を落とす。

標準ライブラリのみで動く。出力は:

| ファイル | 中身 |
|---------|------|
| `out/candidates.md` | 人が読む候補一覧（バケツ別・予備スコア順） |
| `out/candidates.jsonl` | 1行1論文の構造化データ |
| `out/run_meta.json` | 取得/期間外/既出/低スコアの件数 |

候補が0件なら、そう報告して終了してよい。**無理にレポートを埋めない。**
50件を超えたら `keep_top_per_bucket` を下げるか期間を狭める提案をする。

---

**ステップ3: 差分照合**

`out/candidates.jsonl` の各論文について、`state/known-topics.md` の既知主張と突き合わせる。

- 既知の主張と実質同じ → 差分性 0-1点（手法が新しくても上げない）
- 既知の問いに対する新しい答え → 2点
- 既知になかった問い → 3点

同一論文が複数バケツにまたがる場合は、内容を読んで主バケツを1つに確定する。
スクリプトの仮決めが間違っていれば上書きする。

---

**ステップ4: 採点**

[reference/evaluation-criteria.md](reference/evaluation-criteria.md) の5軸で採点する。

要旨だけで採点して構わないが、**S候補（13点以上）だけは要旨に加えて図表と結論を確認する**。
`web_fetch` で `https://arxiv.org/abs/<ID>` を取得するか、PDFを読む。
要旨は著者の主張であって結果ではない。ここを省くとSの精度が落ちる。

減点した論文は、減点理由を必ず記録する（レポートには出さなくてよいが、聞かれたら答えられる状態にする）。

---

**ステップ5: レポート生成**

```markdown
# arXiv 論文トリアージレポート
**対象期間：YYYY年MM月DD日〜YYYY年MM月DD日**

## 今週の要点
[S・A評価を中心に3-5行。論文名の列挙ではなく「何が動いているか」を書く]

## S評価（読むべき）
### [AIの心理学応用] 論文タイトル
- **arXiv**：[2607.27201](https://arxiv.org/abs/2607.27201) / 2026-07-29 / cs.CL
- **何が新しいか**：[既知との差分として1文。「従来は〜だったが、〜」の形]
- **使いどころ**：[工程 × 指標]
- **明日試せる最小検証**：[1つだけ。工数見積付き]
- **落とし穴**：[前提条件・コスト・法務論点]

## A評価（目を通す）
### [バケツ名] 論文タイトル
- **arXiv**：[ID](URL) / 日付
- **要点**：[2文]
- **使いどころ**：[1文]

## B評価（把握しておく）
| バケツ | タイトル | 一行要約 |
|--------|---------|---------|

## 見送り（C評価）
[タイトルとURLのリストのみ]

## 収集メタデータ
- 取得：XX件 / 既出除外：XX件 / 候補：XX件 / 掲載：XX件
- S：X件 / A：X件 / B：X件 / C：X件
```

バケツは必ず日本語ラベルで書く（`psych` 等の内部IDは出さない）。

**S評価の論文は、続けて `paper-explainer` スキルで詳細解説を作ることをユーザーに提案する。**
社内共有向けに読み物化するなら `reframing-storytelling` に渡す。

---

**ステップ6: 品質チェック**

- [ ] S・A が全体の15%を超えていないか（超えていたら基準が緩い。ステップ4に戻る）
- [ ] S評価すべてに「明日試せる最小検証」が書けているか（書けないならA以下）
- [ ] 「何が新しいか」が既知との差分の形になっているか（機能紹介になっていないか）
- [ ] 全論文にarXiv IDとURLが付いているか
- [ ] 台帳の既知トピックと重複する論文を上位に出していないか

---

**ステップ7: 送付と状態更新**

**順序を変えてはいけない。配信が成功してから既出登録する。**

1. Slack送付する場合、mrkdwn に変換して投稿する（下記フォーマットルール）。無人実行では
   `python3 scripts/post_slack.py --report <path>` を使う（分割・スレッド返信・中断からの再開を行う）
2. **配信が成功してから**既出登録する: `python3 scripts/fetch_arxiv.py --mark-seen`
3. **S・A評価した論文を `state/known-topics.md` に1行追記する**（`YYYY-MM | ID | 主張1文 | バケツ`）

3を飛ばすと次回の差分判定が効かなくなる。**このステップが仕組みの心臓部である。**

配信前に `--mark-seen` を呼ぶと、配信が落ちた日の論文が二度と上がってこない。
逆に配信後に呼び忘れると翌朝まったく同じレポートが届く。この2つは同じ順序で
必ずセットにする。`--mark-seen` は既出登録と実行日の記録を同時に行う。

**Slack投稿のフォーマットルール:**

| Markdown | Slack mrkdwn |
|----------|-------------|
| `# 見出し` / `## 見出し` | `*見出し*` |
| `[テキスト](URL)` | `<URL\|テキスト>` |
| `**太字**` | `*太字*` |

1メッセージ約4,000文字が上限。長い場合は分割し、2通目以降は**スレッド返信**にする:

```
1通目（親）: :books: *arXiv論文トリアージ* + 対象期間 + 今週の要点 + S評価
2通目（返信）: A評価
3通目（返信）: B評価 + 見送り + 収集メタデータ
```

送付に失敗したら、レポート本文をチャットにそのまま表示して手動コピーできるようにする。

## 定期実行

平日朝の日次実行を想定している。入口は [scripts/run-daily.sh](scripts/run-daily.sh) で、
GitHub Actions（`.github/workflows/daily-triage.yml`）からも手元からも同じものを叩く。
無人実行時に渡すプロンプトは [prompts/daily.md](prompts/daily.md)。

```
fetch_arxiv.py --daily  →  ステップ3-6（採点・レポート・品質チェック）
                        →  配信  →  fetch_arxiv.py --mark-seen  →  状態をコミット
```

状態と成果物の置き場所は環境変数 `ARXIV_TRIAGE_HOME` で移せる。既定はスキル自身の
ディレクトリなので `~/.claude/skills/` に置いてもそのまま動く。リポジトリ運用では
ルートを渡し、`state/` と `reports/` をルート直下に出している。

**同じ論文を二度出さないための仕組みは4段ある。** どれか1つが欠けると毎朝同じ
レポートが届くので、経路ごとに別々に止めている:

| 経路 | 止める仕組み |
|------|-------------|
| 取得窓が翌日と重なる | `state/seen.json`（ID単位の既出除外） |
| 同じ日に再実行される | `state/runs.json`（配信成功した日付を記録。`--force` で上書き可） |
| 配信が途中で失敗して再送される | `state/slack_posts.json`（親ts と配信済み通数を記録し、続きから再開） |
| 状態ファイルが壊れる／消える | 原子的書き込み + CI では毎回コミットして持ち越す |

**状態ファイルを持ち越さないと重複除外は成立しない。** CI で走らせるなら
`state/` をリポジトリにコミットし直すこと。ephemeral なランナーで毎回まっさらに
なると、毎朝全件が「新着」として上がる。

一方で、**配信が失敗した日は既出登録しない**設計にしている（翌日やり直す）。
重複を防ぐことより取り逃さないことを優先している。

無人実行時も品質チェック（ステップ6）は省略しない。
基準が緩んだレポートが毎朝届く状態が、この仕組みの唯一の失敗モードである。

設定やスクリプトを触ったら回帰テストを通す。取り逃しも重複も静かに起きる:

```bash
python3 scripts/selftest.py         # キーワード（取り逃し）
python3 scripts/selftest_state.py   # 曜日判定・既出除外・二重配信（重複）
```
